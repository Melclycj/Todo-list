# UX-Laws Audit — Todo List App (ux-principles MODE C)

> Date: 2026-06-20 · Read-only static code audit · Lens: Laws of UX (Hick / Fitts / Jakob / Miller / Proximity / Common-Region / Postel / Tesler / Von Restorff / Aesthetic-Usability) + Nielsen's 10 Heuristics + Built-for-Mars teardown.
> Scope: 6 surfaces — shell, auth, tasks (main), topics, archive, recurring, reminder. Frontend at `frontend/src`.
> Evidence is cited to real `file:line`. Severity: **BLOCKER** (ship-stopper / broken contract) / **WARNING** (should fix) / **NOTE** (polish).

## Findings

| # | Severity | Surface | File:line | Law/Heuristic | Issue | Concrete fix |
|---|---|---|---|---|---|---|
| 1 | BLOCKER | tasks | `TaskListPage.tsx:40,117` + `ViewModeDropdown.tsx:6` | H1 Visibility of status / BFM Friction | `viewMode` state is read, persisted to `localStorage`, and surfaced as a "Task Board" option, but `TaskListPage` renders `<TaskList>` unconditionally — `viewMode` is never consumed to switch the view. Selecting "Task Board" silently does nothing; the user gets zero feedback that their choice had no effect. | Either implement the board renderer and branch on `viewMode`, or remove the "Task Board" option from `VIEW_OPTIONS` until it exists. Never ship a control that changes nothing. |
| 2 | BLOCKER | tasks / topics / recurring | `TaskRow.tsx:285,476`; `TaskList.tsx:202`; `SidebarTopicList.tsx:63`; `SubtaskRow.tsx:38-43` | H3 User Control & Freedom / NN "Undo" | No **undo** exists anywhere in the app — confirmed: zero `action:` props on any `toast` call across the codebase. Delete task, delete topic, mark-done, drag-reorder, and subtask-delete are all irreversible from the UI. Deleted tasks do go to Archive (recoverable), but the user is never told that, and topics/reorders/subtasks have no recovery at all. | Add an Undo affordance: `toast.success('Task deleted', { action: { label: 'Undo', onClick: restore } })` for delete/reorder/status; for delete specifically, tell the user it's in Archive ("Deleted — find it in Archive"). |
| 3 | BLOCKER | tasks | `SubtaskRow.tsx:38-43` | H5 Error Prevention / H3 | Subtask delete fires **immediately on click** with no confirmation and no undo — unlike parent-task delete (which has a confirm dialog at `TaskRow.tsx:470`). The trash icon only appears on hover (`SubtaskRow.tsx:53`), so it is easy to mis-click and silently lose a subtask. | Add the same confirm-or-undo treatment as task delete. At minimum, an undo toast (see #2). Inconsistent destructive-op handling within the same surface is the core problem. |
| 4 | WARNING | tasks (a11y) | `App.tsx:87`; whole tree (no `aria-live`, `role="status"`, or `role="alert"` anywhere) | H1 Visibility (a11y) / Postel (output) | Status changes and the **optimistic drag-reorder** (`TaskList.tsx:179-199`) mutate the DOM with no programmatic announcement. `sonner` provides its own live region for toasts, but reorder/inline-edit/topic-change produce **no toast at all**, so a screen-reader or keyboard user gets no feedback that anything happened. Color-only status (see #9) compounds this. | Wrap the task table region in `aria-live="polite"` and announce reorder results ("Moved Task X to position 3"). Ensure every silent mutation (reorder, inline edit save, topic change) has either a toast or a live-region message. |
| 5 | WARNING | tasks | `TaskRow.tsx:470-481` (uses `BulkDeleteDialog` with `count={1}`) → `BulkDeleteDialog.tsx:29` | H4 Consistency & Standards | Single-task delete reuses the bulk dialog, producing the title "Delete 1 task?" and body "permanently delete 1 selected task". For a single row delete the word "selected" is wrong (nothing was selected — it was a row action), and the component name leaks the bulk concept. Minor wording drift but it reads as a bug to users. | Pass the task title into the dialog ("Delete \"Buy milk\"?") or branch copy when `count===1` to drop "selected". Confirms are good; the copy just needs to match the trigger. |
| 6 | WARNING | tasks | `TaskListPage.tsx:101-120`; no `addEventListener('keydown')` / `metaKey` / Cmd+K anywhere (confirmed) | H7 Flexibility & Efficiency / Flow | Zero keyboard accelerators in the entire app: no "N" for new task, no Cmd+K palette, no Cmd+Enter to submit forms, no shortcut for status toggle. A todo app is a power-user, high-frequency surface; everything requires a mouse. Jakob's Law: Linear/Todoist/Things all ship keyboard-first. | Add at least: a global "create task" shortcut, `Esc` already closes editors (good) — extend with `Cmd/Ctrl+Enter` to submit `TaskForm`, and ideally a Cmd+K command palette for filter/topic switching. |
| 7 | WARNING | shell | `Sidebar.tsx:60`; `AppLayout.tsx:81` | H6 Recognition / H1 Visibility | The current location is shown only via the sidebar `NavLink` active state. On mobile the sidebar is hidden behind a hamburger and the top bar shows a static "Todo" (`AppLayout.tsx:81`) — never the current page title, so a mobile user navigating into Topics/Archive/Recurring loses all "where am I" signal until they reopen the drawer. | Render the active page title in the mobile top bar (`AppLayout.tsx:81`) instead of the constant "Todo". Recognition-over-recall: the user shouldn't have to open the drawer to recall what screen they're on. |
| 8 | WARNING | auth | `LoginPage.tsx:33,37`; `RegisterPage.tsx:43` | H9 Error Recovery / H2 Real-world match | Auth errors collapse every failure to one generic string: `'Invalid credentials.'` on any `onError`, and `'Something went wrong. Please try again.'` for network/server errors. A user who is rate-limited, offline, or hitting a 500 gets the same message as a wrong password — no diagnosis, no recovery path. | Differentiate by failure mode: surface the server's `res.error` when present; distinguish network failure ("Can't reach the server — check your connection") from auth failure ("Email or password is incorrect"). |
| 9 | WARNING | tasks | `TaskStatusBadge.tsx:4-9`; `TaskStatusCircle.tsx:4-8` | Law of Similarity / Color (color-blindness) / H1 | Status is communicated **primarily by color** (gray/amber/emerald). The badge does carry a text label (good), but the `TaskStatusCircle` variant is color + a checkmark-only-when-done — todo vs in-progress differ by border color alone with no shape/icon difference. Refactoring-UI color rule: never rely on color alone. | Add a non-color cue to in-progress (e.g. a half-fill or dot) so todo/in-progress are distinguishable without color. Keep the text label on the badge everywhere it's used. |
| 10 | WARNING | tasks | `TaskRow.tsx:386-399` | H5 Error Prevention / Tesler / H9 | Editing the title of a recurring instance is allowed-looking (the cell is rendered, cursor reachable) but on click only fires `toast.info('Titles of recurring task instances cannot be changed')` (`TaskRow.tsx:387`). This is error-by-design: the user tries an action, it's silently refused via a transient toast with no path forward. The constraint should be visible *before* the click. | Render the recurring title visibly non-editable (muted, a small lock/`Repeat` icon, `cursor-default` already set) and drop the toast-on-click, or route the user to the template ("Edit this in Recurring Tasks"). Prevent, don't post-hoc explain. |
| 11 | NOTE | tasks | `TaskRow.tsx:415` | Aesthetic-Usability / H8 Minimalist | Overdue rows use `AlertCircle` with `animate-pulse` (`TaskRow.tsx:415`) — a permanently pulsing icon on every overdue row. With several overdue tasks this becomes persistent motion noise and an accessibility concern (no `prefers-reduced-motion` guard found). | Drop the infinite pulse; a static red icon + red date text already signals overdue (Von Restorff via difference, not animation). If kept, gate behind `prefers-reduced-motion`. |
| 12 | NOTE | tasks | `RowContextMenu.tsx:92-104` | Fitts's Law / Paradox of Active User | The only entry to per-row actions (delete, add subtask) and drag is a 16px grip icon at `opacity-0` until `group-hover` (`RowContextMenu.tsx:98`). It is invisible at rest, small (below the 24-32px desktop target guidance), and undiscoverable for first-time and touch users (no hover on touch). | Increase the hit area (wrap in ≥32px target), and give a faint always-visible affordance (e.g. `opacity-30`) so the action handle is discoverable without hover. |
| 13 | NOTE | shell / tasks | `AppLayout.tsx:43-45`; `TaskTableHeader.tsx:35-37` | Aesthetic-Usability / Polish | The sidebar resize handle is `w-0.5` (2px) and column resize handles are `w-1`/`w-2`; all rely on `cursor-col-resize` + hover color only, with no always-visible grab affordance. Fine on desktop, effectively invisible/unusable on touch. | Acceptable for a desktop-first tool; if mobile matters, widen the grab zones. Listed for completeness — low priority. |
| 14 | NOTE | tasks | `TaskRow.tsx:64-75,134-177` (`EditableCell` popup commits on mousedown-outside) | H3 User Control / Postel | Inline-edit popups **commit on click-outside** (`TaskRow.tsx:66-72`); only `Escape` cancels. A user who clicks away expecting to discard instead saves. This is a defensible choice (and Escape is wired), but it's the opposite of most form mental models. | Keep, but consider: clicking outside an *unchanged* field is fine; for changed content, either keep-saving (current) is OK if there's undo (#2). The real mitigation is the global undo gap. |
| 15 | NOTE | archive | `ArchivePage.tsx:67-76` | Fitts / Discoverability | The "Restore" action is `opacity-0` until row hover (`ArchivePage.tsx:70`). Archive's single most important action is invisible at rest and unreachable on touch. | Make Restore always visible (it's the primary reason to visit Archive), or at least `opacity-60` at rest. |
| 16 | NOTE | tasks | `TaskListPage.tsx:116-120` | Miller / Hick | Header right cluster packs ViewMode + Filter + Search; header left packs title + New Task + edit-mode toolbar. Currently within limits (≤4 per group) so no violation, but the two unlabeled icon-only edit-mode buttons (`TaskEditToolbar.tsx:33,40` — trash + check, `title` attr only) rely on hover tooltips for meaning. | Give the edit-mode trash/done buttons visible text or `aria-label` (only `title` is set today); icon-only destructive controls are a recognition risk. |

## Severity Summary

- **BLOCKER**: 3 (dead "Task Board" view #1, no undo anywhere #2, subtask delete with no confirm/undo #3)
- **WARNING**: 7 (#4 a11y live-region, #5 delete-copy mismatch, #6 no keyboard accel, #7 mobile location, #8 auth error diagnosis, #9 color-only status, #10 recurring-title pseudo-edit)
- **NOTE**: 6 (#11 pulse motion, #12 grip discoverability, #13 resize handles, #14 click-outside-commits, #15 archive restore hidden, #16 icon-only edit buttons)

## Top 5 (ranked)

1. **#1 — "Task Board" view does nothing** (BLOCKER, tasks). A user-facing control with zero effect; either build it or remove it. Highest user-trust damage, smallest fix (delete one array entry to stop the bleeding).
2. **#2 — No undo anywhere** (BLOCKER, all surfaces). Confirms exist on the big destructive ops, but a todo app mutates constantly (status, reorder, topic, subtask) with no recovery. Add undo toasts; tell users deletes live in Archive.
3. **#3 — Subtask delete: no confirm, no undo, hover-only trigger** (BLOCKER, tasks). Inconsistent with parent-task delete and easy to trigger by accident — silent data loss.
4. **#4 — No a11y live region for silent mutations** (WARNING, tasks). Drag-reorder and inline edits announce nothing; combined with color-only status (#9) the app is hard to operate non-visually.
5. **#6 — Zero keyboard accelerators** (WARNING, tasks/shell). No create shortcut, no Cmd+K, no Cmd+Enter submit. A high-frequency tool that's mouse-only fights Jakob's Law against Linear/Todoist/Things.
